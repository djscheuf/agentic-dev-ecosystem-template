# Claude CLI Harness: Requirements

## Bottom line

A `ClaudeHarness` must implement the same `common.harness.Harness` protocol as `DevinHarness`, be swappable via the existing `*_HARNESS` env-var indirection with no workflow-module changes, and reproduce every observable behavior of `DevinHarness` using the `claude` CLI's non-interactive (`-p`) mode instead of `devin -p`. Config loading (`SkillActivityConfig`) is already harness-agnostic and needs no changes. Two structural gaps are not: (1) the vendor-named `devin_log_path`/`atif_path` surfaces must be generalized to `agent_log_path`/`trajectory_path` so the same information is available regardless of which harness ran (a decision, made here — see §2.6); (2) how `SkillActivity` selects which config namespace (`devin` vs. `claude`) to read for a given harness, without requiring an edit to every existing `*.config.json`, is left as an open question (§2.7, §4). The two CLIs also differ in how they surface usage/trajectory telemetry (Devin: one `--export` ATIF file with both aggregate metrics and per-step detail; Claude: no file-export flag at all — aggregate usage and full trajectory both have to be recovered from captured `--output-format stream-json` stdout), so `atif_usage.py` must be generalized rather than duplicated (§2.4.1).

**Status:** Draft — requirements only, no implementation.
**Date:** 2026-09-30
**Scope:** `src/common/claude_harness.py` (new) and its interaction with `common.harness`, `common.skill_activity`, and `common.workflow_logger`.

## Non-goals

- Implementing `ClaudeHarness`. This document only specifies required behavior.
- Changing `DevinHarness` itself or removing it as an option.
- Deciding the final name/shape of generalized (non-`devin`-named) logger accessors — that is called out as an open dependency, not solved here.
- Model-pricing tables, quota policy, or cross-vendor cost normalization.
- Authentication provisioning (API key vs. subscription OAuth token) beyond stating what the harness must assume is already configured in the environment.

## 2. Required behavior for `ClaudeHarness`

### 2.1 Interface contract

- MUST satisfy `common.harness.Harness` structurally: `run(self, prompt: str, *, cwd: Path, config: Mapping[str, object]) -> HarnessResult`.
- MUST have a zero-argument constructor (optionally with a keyword-only `runner` override, mirroring `DevinHarness.__init__(self, *, runner=subprocess.run)`), so it can be instantiated by `harness_instance.py`'s `cls()` call with no changes to that loader.
- MUST be loadable via the existing `<WORKFLOW>_HARNESS=module:ClassName` env-var convention without modifying `story_design_workflow`, `story_analysis_workflow`, or `edd_refinement_workflow`'s `harness_instance.py`.

### 2.2 Invocation shape

- MUST invoke the `claude` binary non-interactively via `claude -p ... -- <prompt>` (or equivalent flag ordering), run with `cwd=cwd`, `capture_output=True`, `text=True`, one process per `run()` call.
- MUST set `--permission-mode` explicitly on every invocation. `-p` defaults to Manual (read-only) mode, which would otherwise hang or fail waiting for approval in an unattended skill Activity — never rely on the CLI default.
- MUST set `--model` explicitly (no reliance on the ambient default model), mirroring Devin's `--model` requirement.
- SHOULD evaluate `--bare` (or `--strict-mcp-config` / explicit `--setting-sources`) to suppress auto-discovery of `.claude/` skills, hooks, MCP servers, and CLAUDE.md during unattended skill-activity invocations, since undiscovered trust dialogs or project hooks could otherwise block a non-interactive run with no prompt host attached. This is an **open question** (§4) because `--bare` also strips the skill/subagent machinery that some callers may need loaded for the skill prompt to resolve correctly — it cannot be a blanket default without checking what each skill prompt actually depends on from `.claude/`.
- MUST pass the full skill prompt as the final positional argument after `--`, matching Devin's `-- <prompt>` convention, to avoid prompt text being misparsed as flags.

### 2.3 Config namespace and validation

- The `SkillActivityConfig`/`SkillActivity` loading path (§1) is already harness-agnostic and requires **no changes** to support a second harness: it validates structure (`activity.*`, `harness` is an object, `schema.artifact_schema_path`), never a namespace's contents, and passes the frozen `harness` mapping through opaquely. All namespace-specific parsing/validation belongs entirely inside the harness class itself (`ClaudeHarnessConfig.from_mapping`, mirroring `DevinHarnessConfig.from_mapping`) — this is a boundary to preserve, not re-derive.
- `from_mapping` MUST accept any `Mapping[str, object]`, including the `MappingProxyType` instances `SkillActivityConfig._freeze` produces (read-only, not a plain `dict`). It must use `.get`/membership checks only — `DevinHarnessConfig.from_mapping` already does this correctly and `ClaudeHarnessConfig.from_mapping` must follow the same pattern (no `dict(config)` copies that assume mutability, no `isinstance(x, dict)` checks that would reject a `MappingProxyType`).
- MUST read a `config["claude"]` namespace, leaving other top-level namespaces (`config["devin"]`, `config["other"]`) untouched — mirrors `DevinHarnessConfig.from_mapping`'s namespace isolation so a single `*.config.json` could in principle carry both `devin` and `claude` blocks during a migration window.
- MUST reject unknown keys inside `claude.*` the same way `DevinHarnessConfig` rejects unknown keys inside `devin.*` (`unknown_key: claude.<key>`).
- MUST reject invalid `model` (non-string or blank) and invalid `permission_mode` (outside the harness's supported set) with the same `invalid_value: claude.<field>` error convention.
- MUST define its own `SUPPORTED_PERMISSION_MODES` frozenset scoped to values the `claude` CLI actually accepts (`default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` per the CLI's documented modes) — these are **not** the same literal strings as Devin's (`auto`, `accept-edits`, `dangerous`, `bypass`). A `claude.permission_mode` value must not silently accept a Devin-shaped string that happens not to error.
- MUST pick secure defaults: a mode that denies rather than silently allows anything that would otherwise prompt (`dontAsk` is the closest CLI equivalent to "fail closed" for a skill Activity with no attached prompt host) unless a specific skill's config explicitly opts into a more permissive mode — mirrors ADR-012's "least privilege by default, opt in per skill" decision.

### 2.4 Usage/cost telemetry and conversation trajectory

This is the behavior most structurally different between the two CLIs and must not be ported as a literal file-export mechanism. Devin produces **both** aggregate usage *and* a full step-by-step trajectory in one artifact (the ATIF file). For Claude, usage and trajectory come from different output-format choices, and the harness needs both:

- `--output-format json` returns one JSON object on stdout only after the whole turn completes: `result` (text), `session_id`, `total_cost_usd`, and a usage breakdown. This is sufficient for aggregate usage but discards per-step detail (tool calls, intermediate messages) — it is not a trajectory.
- `--output-format stream-json` (with `--verbose`, per the CLI reference) emits NDJSON: a `system/init` event, then one event per message/tool-call/tool-result as they happen, then a final `result` line. This is the closer analog to Devin's ATIF `steps` array, and is the mechanism that must be used if the harness is to reproduce Devin's "exported trajectory" capability rather than only its "exported aggregate usage" capability.

Requirements:

- MUST request `--output-format stream-json --verbose` (not plain `json`) so that both the full step-by-step trajectory and the final aggregate `result`/usage line are available from a single invocation — mirroring Devin's single `--export` producing one ATIF document that contains both `steps` and `final_metrics`.
- MUST capture the NDJSON stream as it is already captured today (`capture_output=True, text=True` on `subprocess.run`) — no new CLI flag is needed to get the data off the process; `--export <path>` is a Devin-specific mechanism with no Claude CLI equivalent. The "export" step for Claude is: write the captured stdout text to a trajectory file, not: ask the CLI to write one itself.
- MUST write the captured NDJSON stdout to a durable artifact file (e.g. `claude-trajectory.jsonl` or `agent-trajectory.jsonl` — see §2.6 naming decision) beside `activity.log` when running inside an Activity logging context (`get_activity_artifact_dir()` is set), exactly mirroring `DevinHarness`'s durable-vs-temporary split: durable when an Activity context exists, a parse-then-discard temporary file otherwise. This reuses the existing `get_activity_artifact_dir()` contract from `workflow_logger` — no new logger plumbing is required for *this* part.
- MUST parse the **final** NDJSON line (the terminal `result` event) to extract aggregate usage, independent of whether the trajectory file is retained. Usage extraction must not require re-reading the whole trajectory for every call if only the last line is needed — iterate from the end, or track the last line while streaming/writing.
- MUST still separate "the text a human/skill cares about" (equivalent to today's `HarnessResult.stdout`) from "the raw stream-json trajectory." Options for `HarnessResult.stdout` semantics are an **open question** (§4): return the final `result` event's text field (parity with what a prompt author expects to read) vs. return the full raw NDJSON blob (literal parity with Devin's "stdout is whatever the subprocess printed" contract, since Devin's `-- "..."` stdout is also plain text, not JSON — the two CLIs are not symmetric here either). This document does not pick one — it flags that the choice changes what every caller of `HarnessResult.stdout` can assume.
- MUST treat usage parsing as best-effort and non-fatal: malformed/missing/truncated NDJSON (e.g. the process was killed mid-stream, or printed a plain-text error before producing any structured event) MUST NOT change `exit_code`, and MUST NOT raise — mirrors the Devin contract's "missing/malformed telemetry never changes a successful or failed Devin result" invariant, verified today by `test_run_with_missing_or_malformed_export_preserves_process_result`.
- MUST normalize only fields with a stable, confirmed meaning onto the shared `HarnessUsage` dataclass (`prompt_tokens`, `completion_tokens`, `cached_tokens`, `cost_usd`). Field-name mapping from the Claude CLI's terminal `result` event to these four attributes must be confirmed by direct characterization (see §4) before being hardcoded — same discipline `docs/reqs/capture-cost-metrics/streams/devin-atif-characterization.md` applied to Devin's `final_metrics` keys before `read_atif_usage_result` was written.
- MUST reject boolean values presented where an integer token count is expected, consistent with `_token()`'s existing behavior (reused, not reimplemented — see §2.4.1).
- Raw-trajectory retention is subject to the same secrets/audit rules as today's ATIF retention (§2.6): never copied into `activity.log`, sanitized diagnostics only, same artifact-directory lifecycle.

#### 2.4.0a Ground truth: observed ATIF structure and its Claude equivalent

Reviewed directly: [`docs/reqs/claude-harness/example.devin-trajectory.json`](example.devin-trajectory.json) — a real `audit-current-reality` skill invocation (`ATIF-v1.7`, 22 steps). This replaces assumption with inspection and grounds the "extract tokens, real USD cost, and the sequence of agentic actions (prompts, skills, tool calls)" requirement in concrete structure:

| ATIF element (observed) | Shape | Claude `stream-json` equivalent | Notes |
|---|---|---|---|
| `schema_version` ("ATIF-v1.7") | top-level string | none | `stream-json` is an NDJSON event stream, not a single versioned document. If the harness writes its own trajectory file (§2.4), *it* must stamp a schema version, since the CLI gives it none. |
| `session_id` | top-level string | `session_id` field, present on every event | Direct equivalent; already surfaced today via `--output-format json`'s `session_id`. |
| `agent.{name,version,model_name,tool_definitions}` | top-level object | `system`/`init` event (`model`, `tools[]`, `mcp_servers[]`, …) | Direct equivalent — first NDJSON line. |
| `steps[]` with `source: "system"` (7 of 8 are static system-prompt/rules/skill-list injections, logged once per session) | step objects, `message` = full prompt text | Not emitted as discrete events in `stream-json` (system prompt is sent, not streamed back) | **Gap, not a mapping.** ATIF logs the entire system prompt (identity, modes, rules, `<available_skills>` listing) as explicit steps; Claude's `stream-json` does not echo the system prompt back at all — only `system/init`'s metadata (model, tool list) is visible. A Claude trajectory file will *not* contain the equivalent of ATIF steps 1–7, 9 unless the harness captures the prompt it sent separately (it already has this — `SkillActivity.build_prompt()`'s output — so it should be stored as the trajectory's first synthetic entry rather than assumed recoverable from the CLI). |
| `steps[]` with `source: "user"` (step 8: literally `"Invoke the 'audit-current-reality' skill.\nInput document path(s): ...\n..."`, i.e. the exact text `SkillActivity.build_prompt()` produced) | one step, full prompt text | The `-p` positional prompt argument itself | **The "skill" in ATIF is not a structured field — it's parsed back out of this free-text instruction** (exactly as `tests/fake_harness.py`'s `_parse_skill_name` does via regex on `"Invoke the '([^']+)' skill"`). A Claude trajectory does not need this: the skill name is already known to the harness caller (`SkillActivityInput.skill_name` / `self.skill_name`) before the prompt is even built, so the harness can record it directly rather than re-deriving it from text. |
| `steps[]` with `source: "agent"` (13 of 22): `reasoning_content` (free text), `tool_calls[]` (`tool_call_id`, `function_name`, `arguments`), `observation.results[]` (`source_call_id` ↔ `tool_call_id`, `content`) | one step per agent turn | `assistant` message events, each with `content[]` blocks of type `text`, `thinking`/`redacted_thinking`, and `tool_use` (`id`, `name`, `input`); matching `tool_result` content blocks arrive on the following `user` message, correlated by `tool_use_id` | **This is the real analog of "sequence of agentic actions."** Structurally equivalent to ATIF's `tool_calls`/`observation.results` pairing, just split across alternating `assistant`/`user` events instead of one step's `tool_calls`+`observation`. A Claude-harness trajectory parser needs to walk the NDJSON stream and correlate `tool_use.id` → subsequent `tool_result.tool_use_id`, mirroring what ATIF already gives for free via `source_call_id`. |
| Per-step `metrics` (`prompt_tokens`, `completion_tokens`, `cached_tokens` — **cumulative across the session**, confirmed by inspection: step 10 → 14471, step 22 → 93829 prompt tokens, monotonically increasing) | present on `agent`-source steps only | Anthropic Messages API `usage` object on each `assistant` message | **Assumption (unverified): treat Claude's per-message `usage` as cumulative across the session, matching ATIF's pattern.** This is a working assumption, not a confirmed fact — see "Assumption: cumulative usage accounting" immediately below the table. |
| Per-step `extra.committed_acu_cost` (Devin's proprietary "Agent Compute Unit" billing fraction; sums to `0.1044` ACU across all 22 steps in the example — **not USD**) | present on every `agent` step | `total_cost_usd` on the final `result` event (per the CLI reference, confirmed to exist in `--output-format json`'s single JSON object) | **This is the one place `ClaudeHarness` can do strictly better than `DevinHarness` today.** The observed Devin export has **no `total_cost_usd` field at all** — ADR-015 and the ATIF characterization both confirm Devin currently reports zero USD cost, only a proprietary per-step ACU fraction with no documented USD conversion. Claude's CLI documents a real `total_cost_usd` directly. `HarnessUsage.cost_usd`, which is `None` for every real Devin invocation in this repo today, should be non-`None` for `ClaudeHarness` invocations once the final `result` event is parsed — this is a concrete, user-requested capability gap this story can close, not just parity work. |
| `final_metrics` (session-level totals: `total_prompt_tokens`, `total_completion_tokens`, `total_cached_tokens`, `total_steps`; no cost field) | top-level object | Final `result` event's `usage` object + `total_cost_usd` + (if present) a turn/step count | Direct equivalent for everything except cost, where Claude is additionally populated (previous row). |

**Assumption: cumulative usage accounting (2026-09-30).** This document assumes each `assistant` message's `usage` object in `--output-format stream-json` reports *cumulative* token counts for the session so far, the same pattern ATIF's per-step `metrics` exhibit, rather than a per-turn delta. This repo has no verified documentation for this claim — it is carried here only because it is the most plausible reading currently available, with no citable source. Treat it the same way ADR-015 treated "assume ATIF totals include subagent usage": a stated, named assumption the implementation depends on, not a confirmed contract. If a Claude trajectory parser is built against this assumption and summing per-message usage double-counts tokens (because the real behavior is per-turn deltas, as standard Anthropic Messages API usage objects normally are), that will show up as `HarnessUsage.prompt_tokens`/`completion_tokens` being roughly `N`× too large for an `N`-turn session — a cheap sanity check once a real multi-turn trace is available. The parser should prefer reading usage off the single terminal `result` event (which is documented to carry session totals regardless of accumulation style) over summing per-message usage, specifically so this assumption only matters if per-message usage is consulted at all; characterization (§4, open question 1) still owns confirming or retiring the assumption.

**Requirement, made concrete by this inspection:** a Claude trajectory file (§2.4) must preserve, per turn: the turn's reasoning/text content, every tool call with its arguments, every matching tool result, and that turn's usage — i.e. it must reconstruct the same "what did the agent do, in order, and what did each step cost" narrative that ATIF's `steps[]` array already gives for Devin, even though Claude's `stream-json` delivers the same information shaped as alternating `assistant`/`user` events rather than one unified step record. Skill identity (which skill was invoked) does **not** need to be parsed back out of prompt text for Claude the way `fake_harness.py` does for Devin — the harness already has `skill_name` from `SkillActivityInput` before it builds the prompt, and should attach it to the trajectory directly as a top-level field rather than re-deriving it.

#### 2.4.1 Required generalization of `atif_usage.py`

`src/common/atif_usage.py` is Devin-specific in both name and shape: it reads one JSON document from a file path and reaches into a hardcoded `final_metrics` key. Adding a second harness with a structurally different telemetry source (NDJSON stream, final-line extraction, no `final_metrics` key) must not result in a second copy-pasted parser with duplicated `_token`/`_cost` coercion logic. This document requires the following refactor as part of the Claude-harness effort, not as a separate follow-up:

- Extract the vendor-independent coercion helpers (`_token`, `_cost` — "reject bool, accept only well-typed numeric values") into a shared module (e.g. `common/harness_usage.py`) that both Devin's and Claude's parsers import. These helpers have zero Devin-specific logic today and are already a straight duplication risk.
- Keep (or move) the Devin-specific entry point — reading one JSON file, extracting `final_metrics` — as a thin adapter in that shared module or a `devin`-suffixed sibling (`read_atif_usage_result`), unchanged in observable behavior (same four failure categories: `missing_export`, `unreadable_export`, `malformed_json`, `invalid_final_metrics`/`invalid_document`).
- Add a Claude-specific entry point (e.g. `read_claude_usage_result`) with its own failure-category vocabulary appropriate to NDJSON parsing (e.g. `missing_output`, `empty_stream`, `malformed_json_line`, `missing_result_event`) that returns the same `(HarnessUsage | None, str | None)` shape so both harnesses' logging code (§2.6) can log a `error_category` field generically regardless of which harness produced it.
- The two source-specific functions MUST converge on the same `HarnessUsage` dataclass and the same tri-state contract (populated usage / `None` with a reason / never raises), so that any future consumer of usage data (reporting, aggregation) does not need to know which harness produced a given `HarnessResult`.
- This generalization is in scope for the Claude-harness story because the duplication would otherwise be introduced *by* this story — it is not optional cleanup bolted on afterward.

### 2.5 Error handling

- MUST catch `OSError` from process launch (binary not found, permission denied, etc.) and re-raise as `RuntimeError("claude_launch_failed")`, after logging an `error_category=claude_launch_failed` message on both loggers — direct parallel to `devin_launch_failed`.
- MUST pass through the subprocess's `exit_code`, `stdout`, and `stderr` unchanged for every other failure mode (non-zero exit, usage-parsing failure), matching Devin's "process result is sacred, telemetry is observational" invariant.

### 2.6 Logging

- MUST emit the same event taxonomy shape as `DevinHarness`, adapted to the new vendor: a `SelectClaudeTelemetrySource` (or equivalently-named) event before invocation describing storage mode, a `StartClaudeInvocation` event with skill name/model/permission mode, and a `CompleteClaudeInvocation` event with exit code, duration, and usage-availability boolean.
- MUST emit a `RejectUsageTelemetry`-equivalent warning (sanitized error category only) when usage parsing fails, without logging the raw stdout/response content that produced the failure.
- MUST NOT log prompt text, raw CLI stdout/response content, or any session transcript content at `INFO` level; raw stdout/stderr may be logged at `DEBUG` level into a per-invocation log file, mirroring today's `devin_logger.debug` dump of `result.stdout`/`result.stderr`.
- Dual-logger plumbing (`get_activity_logger()`, a vendor-specific logger, `get_activity_artifact_dir()`) is reused from `common.workflow_logger` as-is for the durable/temporary storage-mode distinction that still applies to log files and any retained raw-response artifact, even though it no longer applies to usage-extraction itself.
- **Decision: generalize `devin_log_path` to `agent_log_path`.** Rather than leaving this as an open question, the vendor-named surface must be renamed to a harness-agnostic one, with the invariant that *the same information* (the per-invocation CLI log file for whichever harness actually ran) is available at the end of that path regardless of which harness produced it. This requires coordinated changes across every layer that currently hardcodes `devin`:
  - `common.workflow_logger`: add `get_agent_logger()` / `get_agent_log_path()` (or rename the existing `get_devin_logger()`/`get_devin_log_path()` outright — a straight rename is preferable to running two parallel accessor pairs, since both the Devin and Claude harness code paths should log through the same named surface). The underlying file itself (`devin.log` today) should also be renamed to something harness-neutral (e.g. `agent.log`) so the directory layout under `.process/logs/<workflow>/<run>/activities/<attempt>/` doesn't keep a vendor name once a second vendor exists.
  - `common.skill_activity.SkillActivityOutput.devin_log_path` → `agent_log_path`, and the local variable/call site in `SkillActivity.execute()` (`devin_log_path = get_devin_log_path()`) updated to match.
  - `src/story_analysis_workflow/schemas/story-analysis-report-v1.schema.json`: the required `devin_log_path` property (and its presence in the `required` array alongside `activity_log_path`) must become `agent_log_path`. This is a breaking schema change for anything already validating against `story-analysis-report-v1` — bump the schema version or add a migration note if existing report artifacts must remain valid against the old name.
  - `DevinHarness` and `ClaudeHarness` both populate whatever `agent_log_path` resolves to; neither harness owns the name.
  - The equivalent `atif_path` field in `SkillActivity.execute()`'s `observation` dict (currently Devin-specific, pointing at `devin-trajectory.json`) should receive the same treatment — generalize to something like `trajectory_path` so it can point at either `devin-trajectory.json` or the Claude trajectory file from §2.4 without a second vendor-specific field name.

### 2.7 Skill-activity integration dependency

- `SkillActivity.execute()` (`src/common/skill_activity.py`) hardcodes `self.harness_config.get("devin", {})` to populate `observation["model"]` and `observation["permission_mode"]`. **This will silently produce empty/wrong values if `ClaudeHarness` is swapped in with a `config["claude"]` namespace and `SkillActivity` is not updated.** A `ClaudeHarness` cannot fix this from inside its own `run()` method — it is a caller-side coupling, structurally identical to the `agent_log_path` rename in §2.6 but for the config-read side rather than the log-write side.
- Every one of the ~10 existing `*.config.json` files (`analyze_story.config.json`, `grade_story_analysis.config.json`, etc.) nests its harness options under a hardcoded `"harness": {"devin": {...}}` key today. Swapping which harness class runs (via the existing `<WORKFLOW>_HARNESS=module:ClassName` env var) does **not** currently change which namespace key `SkillActivity.execute()` reads for observation reporting — it is a Python-level string literal (`"devin"`), not derived from the harness instance in any way. So the harness swap and the config-namespace-read are two independently-wired things today, and only one of them (the harness class) is swappable without editing files.

**Open question — how is the config namespace selected without updating every config file?** This document does not resolve it; it must be decided before `ClaudeHarness` is wired into any real workflow. Candidate shapes, none chosen:

- The harness instance exposes its own namespace (e.g. a `ClaudeHarness.CONFIG_NAMESPACE = "claude"` class attribute, parallel to `DevinHarness`), and `SkillActivity.execute()` reads `self.harness_config.get(self.harness.CONFIG_NAMESPACE, {})` generically instead of the literal `"devin"`. This removes the hardcoded string but still requires every `*.config.json` to carry the *right* namespace key for whichever harness is currently configured via the env var — i.e. it fixes the Python-side coupling but not the "every config file still needs a `claude` block to switch" problem.
- `SkillActivity` tries each known namespace (`devin`, then `claude`, ...) and uses whichever is present — fragile if a config file is meant to carry both during a migration window, and reintroduces a hardcoded list of known vendor names in a different place.
- The config file stops naming a vendor-specific namespace at all and instead the harness is responsible for interpreting whatever single `harness` object it's given (no namespace key) — this is the most future-proof shape but is a breaking change to every existing `*.config.json`'s structure, not just an additive one.
- Namespace selection happens one level up, outside the config file entirely (e.g. an env var or a field in `activity.*` names the active harness profile, and that name is used to look up both the harness class *and* the config namespace in one place) — keeps `*.config.json` files vendor-named but centralizes the one place that has to know both facts simultaneously.

Each of these trades off "how many files need to change when adding a second harness" against "how much hardcoded vendor-name knowledge lives in `common`." Resolving this is a prerequisite for running `ClaudeHarness` against any workflow whose `*.config.json` files are shared with `DevinHarness` today.

### 2.8 Non-interactivity and environment assumptions

- MUST assume authentication is already configured in the executing environment (`ANTHROPIC_API_KEY`, `apiKeyHelper`, or a pre-provisioned `CLAUDE_CODE_OAUTH_TOKEN`) — the harness does not provision credentials.
- MUST NOT rely on any interactive approval path (no prompt host is attached to a Cadence Activity subprocess); whichever permission mode is selected per §2.3 must be one that cannot block waiting for a human.
- SHOULD consider `--no-session-persistence` or equivalent to avoid accumulating `~/.claude/projects/` transcripts for every skill-activity invocation in CI/worker environments, unless the project wants those transcripts retained for audit (which would itself need the same secrets/retention review called out in §2.6).

## 3. Testing requirements (parity with `test_devin_harness.py`)

A `ClaudeHarness` test suite must cover the same scenario classes as `src/common/tests/test_devin_harness.py`, adapted to the new config namespace and telemetry source:

1. Translates only the `claude` config namespace to CLI flags; other namespaces (e.g. `devin`) are ignored; accepts a `MappingProxyType`-frozen config (not just a plain `dict`) the way `SkillActivityConfig.load` actually produces it.
2. A successful run with a valid terminal `result` event in the NDJSON stream returns populated `HarnessUsage` and preserves `exit_code`/`stdout`/`stderr`.
3. A non-zero exit still returns any usage that was parseable from the stream (usage capture is independent of exit code).
4. Missing, truncated, or malformed NDJSON output preserves the original process result and returns `usage=None`, for both successful and failing exit codes.
5. Boolean values presented as token counts are rejected independently per field, consistent with sibling fields remaining valid — exercised against the shared coercion helpers from §2.4.1, not a second copy of `_token`/`_cost`.
6. Logging emits sanitized storage/availability/error-category metadata without leaking prompt text or raw CLI response/trajectory content (equivalent to the `marker not in caplog.text` assertion pattern already used).
7. `OSError` on process launch is converted to `RuntimeError("claude_launch_failed")`, with both loggers recording the failure before the exception propagates.
8. Path/identifier sanitization for any artifact directories reused from `activity_log_context` behaves identically to the existing Devin tests (retry-attempt isolation, path-unsafe identifier sanitization) — this is inherited behavior from `workflow_logger`, not new to the harness, but must still be exercised against `ClaudeHarness`'s actual code path.
9. Existing three/four-field `HarnessResult`/`HarnessUsage` construction remains valid — no changes to those shared dataclasses are implied by adding a second harness.
10. The captured NDJSON trajectory is written to the Activity artifact directory (durable) when an Activity context is active, and to a temporary file that is parsed then removed otherwise — direct parallel to `test_run_with_activity_context_retains_trajectory_beside_activity_logs` / `test_run_without_activity_context_exports_parses_and_cleans_temporary_trajectory`.
11. `read_claude_usage_result` (§2.4.1) is tested independently of `DevinHarness`/`ClaudeHarness` process plumbing, the same way `atif_usage.py`'s parser is unit-tested in isolation from `DevinHarness` today — including its own missing/empty/malformed-line/missing-result-event failure categories.

## 4. Open questions (require characterization before implementation)

Mirrors the precedent set by `docs/reqs/capture-cost-metrics/streams/devin-atif-characterization.md`, which ran one real `devin -p --export` invocation before committing to field names. The same discipline applies here:

1. **Exact `--output-format stream-json` schema, including confirming the cumulative-usage assumption.** What are the literal field names for prompt/completion/cached token counts and cost on the terminal `result` event, and on each `assistant` message's `usage` object? This document currently *assumes* (see "Assumption: cumulative usage accounting" in §2.4.0a) that per-message usage is cumulative across the session, matching ATIF's pattern — stated explicitly as an unverified working assumption rather than a confirmed fact, since no citable documentation was found for it either way. Run one minimal authenticated `claude -p --output-format stream-json --verbose "Reply with exactly OK."` invocation and inspect the real NDJSON before writing a parser — same discipline as the existing Devin ATIF characterization — and run a second, multi-turn invocation specifically to confirm or retire the cumulative-usage assumption, since a single-turn example can't distinguish "cumulative" from "per-turn." Until that characterization runs, the parser should prefer the terminal `result` event's totals over summing per-message usage, so the assumption only matters where per-message usage is consulted directly.
2. **`HarnessResult.stdout` semantics.** Should it carry the terminal `result` event's text field (what a prompt author expects to read) or the full raw NDJSON blob (literal parity with "whatever the subprocess printed to stdout")? Note Devin's own stdout is plain text, not JSON, so "parity with Devin" doesn't resolve this either way on its own. This decision affects every downstream consumer of `HarnessResult.stdout` and is not purely a harness-internal choice.
3. **Permission-mode mapping.** Devin's four modes (`auto`, `accept-edits`, `dangerous`, `bypass`) do not map one-to-one onto Claude's six (`default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`). In particular, Devin's `auto` ("everything, no asking") is closer in intent to Claude's `bypassPermissions` than to Claude's `auto` (which still runs a background classifier on shell/network actions and can still prompt). Per-skill config migration must not assume string-identical modes carry the same risk profile.
4. **`--bare` default.** Does suppressing `.claude/` skill/hook/MCP discovery break any skill prompt that currently depends on project-level Claude Code configuration being loaded, or is every skill prompt today self-contained text with no such dependency? Needs a check against actual skill prompts under `.devin/skills/` (or wherever the project's skill definitions live) before deciding `--bare` is safe as a default.
5. **Config-namespace selection without touching every `*.config.json` (§2.7).** How does `SkillActivity` (or whatever replaces its hardcoded `"devin"` read) know which namespace to pull from a shared `harness` config block when the active harness class changes, without requiring an edit to every one of the ~10 existing per-skill config files? §2.7 lists four candidate shapes and picks none of them — this needs a decision from whoever owns `common.skill_activity` before `ClaudeHarness` can run against a real workflow, not just against `harness_instance.py`'s direct-override test path.
6. **Raw-trajectory retention policy.** Devin's ATIF trajectory is retained by default (ADR-015: "durable export remains the recommended default... workflow actions are intended to be auditable"). Does the same retention default apply to Claude's captured NDJSON trajectory (§2.4), given it may be considerably larger/more verbose than ATIF's `steps` array (per-token streaming deltas, hook events, etc., depending on which stream extras are enabled)? Is the plain `result`-only event sufficient for audit, or is the full per-step stream required for parity?
7. **Schema migration for `agent_log_path`/`trajectory_path` (§2.6).** Renaming `devin_log_path` → `agent_log_path` in `story-analysis-report-v1.schema.json` is a breaking change to a committed schema. Does this repo have any existing persisted report artifacts that validate against the old required field name, and if so, does the rename need a schema version bump (`story-analysis-report-v2`) or an in-place migration?
